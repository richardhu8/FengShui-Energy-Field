寻炁拆解与对策

xunq.chat 是什么、怎么搭的、哪些难哪些不难，以及我们手上已有的牌该怎么打。

一句话结论：它的 3D 可视化确实领先，但底层术数引擎比我们弱得多—— 它的九星排盘在自己的代码注释里写着「简化排盘」，只飞一颗星，没有山星向星。 我们该抄的是它的呈现方式，不是它的算法。

/xunqi/ 那页是 464 KB 的单个 HTML，其中 380 KB 是内联 <script>。 自有 JS 文件只有三个：three.min.js、walls.js、stars.js。

这对我们是好消息

它的工程复杂度很低——和我们现在的单文件 HTML 是同一种做法，只是规模大。 没有 React/Vue/构建链要追赶，不存在「技术栈代差」。难的是内容量和 3D 效果，不是架构。

03后端只有一个接口

全站唯一的服务端调用是 POST /api/chat——AI 堪舆师的 LLM 代理：

  • 请求体 {messages: 最近8条, context: 当前盘面摘要, image?: 截图}
  • 30 秒超时 + AbortController + JSON content-type 校验（代码注释显示是踩过网关错误页的坑后补的）
  • 限流：每个匿名浏览器每天 3 次；带图提问默认关闭

命书另有一个 /mingshu-api/feedback，看名字只是反馈收集。 没有账号系统、没有数据库、盘面状态只存 localStorage。

04三个「看起来很难」的功能，实际怎么做的

① 户型图上传 → 墙体识别

我一开始以为用了 OpenCV，查证后是我看错了（代码里的 cv 只是 canvas 变量名）。 实际是手写的像素管线，函数名可见：

analyzeWalls · buildWallEvidence · cleanWallGrid · despeckleWall · appendDiagonalWalls · countWallCells

配合 getImageData + 阈值二值化 + 膨胀（dilate）+ 去噪，落成一张网格。 没有机器学习。而且界面明说「上传后请核对红色墙线；不准可用直线/画笔修正」—— 识别不保证准确，靠人工兜底。默认演示场景 walls.js 干脆是一张写死的 192×117 位图。

可复制性：高。阈值+形态学是标准图像处理， 不需要 ML。真正的工作量在交互修正工具（直线/画笔/吸附）上。

② 3D 炁流场

Three.js + WebGL2。控制台暴露的参数说明了模型：主炁口朝向、扩散角度、炁速、 能量强度、粒子寿命、增加炁口/出口。本质是从入口发射、受墙体阻挡的粒子/热力场， 再把九宫标签立在 3D 空间里。还叠了潮汐、月相、星图。

可复制性：中等偏难。 这是它唯一真正的技术护城河。不是算法难，是调参和美术难—— 要让流场看起来「像那么回事」需要大量视觉打磨。

③ 实景罗盘（陀螺仪）

浏览器 DeviceOrientation API。iOS 需要用户手势授权 + HTTPS。

可复制性：高。几十行代码，坑主要在 iOS 权限和磁偏角校正。

05它的软肋：术数引擎

这是这次拆解最有价值的发现。它的 stars.js 只有 3.8 KB，文件头自己写着 「玄空九星（时家紫白·阳顺简化排盘）」。看代码：

问题一：时家紫白是假的

starOfHour(i) = (i % 9) + 1——「子时一白起，逐时辰顺行」。 真正的时家紫白要按日支分三组、再分冬至后阳遁顺行 / 夏至后阴遁逆行。 我们的引擎实现了完整规则，并与抖音那套 App 实测对上（流时中宫 6 白）。

问题二：没有山星向星

它只把一颗星（年星或时星）入中宫顺飞，得到一张九宫。 但玄空飞星的核心是依坐向排山盘 + 向盘双星——这才有旺山旺向、双星到向、上山下水的格局判断。 它这套严格说只是紫白飞星，不是玄空飞星。

问题三：时区口径自相矛盾（已实测复现）

同一时刻，/kanyu/ 显示时柱 乙未，/xunqi/ 显示 己丑。 我用我们的引擎两种都复现了：按北京时间算得乙未、按浏览器本地时间算得己丑—— 一个模块用北京时间、另一个用本地时间。海外用户看到的时柱是错的。

它做对的部分也要说清楚：流年紫白公式正确（(11-year%9)%9，2026→一白，与我们一致）， 洛书飞泊路径也正确。九星的 luck 数值（1.00 / 0.15 / 0.05…）是为可视化设计的启发式权重， 不是传统定数——用来驱动能量强度合理，但不该当断语。

06建议路线

不要正面复刻。它领先的是广度和视觉，我们领先的是正确性和可验证性—— 在术数产品里，「算得对」是可以做成卖点的，因为用户根本没法自己检验。

  1. 把已有引擎的优势显性化
    成本低、见效快。在页面上直接展示「与 N 个独立实现逐格校验」的证据， 公开算法规格与测试。这是它给不出的东西。
  2. 补户型图上传 + 墙体识别
    阈值二值化 + 形态学 + 人工修正工具。我们已有多边形编辑器和缺角分析， 上传只是把「手动画」换成「自动描 + 手动修」。技术风险低。
  3. 补 AI 解读
    一个 /api/chat 代理即可，参考它的做法：带盘面 context、 限流、超时保护。我们的优势是能把可验证的盘面数据喂给模型，而不是让模型瞎编。
  4. 再考虑 3D
    Three.js 粒子流场。这是投入最大的一块，建议放在有真实用户反馈之后， 不要一上来就啃。

两个要提前想清楚的问题

  • 合规：它挂了 AdSense、写「仅供传统文化参考」、AI 回答有免责声明、 命书标题特意写「传统命理文化科普」。这套措辞是有意为之，我们也需要。
  • 流派分歧：它直接给「宅局综合评分」，但下卦/替卦分界、井字法vs放射法、 五入中阴阳这些差异会直接改变结论。我们目前的做法是两派都给、分歧如实列出—— 这更诚实，但要想清楚普通用户是否买账。

方法：公开页面与静态资源的架构分析（HTTP 头、脚本清单、公开 JS 逻辑、页面体量）， 未做任何侵入性测试。术数结论均以我们已验证的引擎实算交叉比对。

标注为「未见 / 未验证」的项目表示本次未查到证据，不等于该功能不存在。
